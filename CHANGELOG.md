# Changelog

Versions follow SemVer, newest first.

## Unreleased

- Links to the documentation point to https://mcp.aiwcorpo.pl/2.0/ (the pages under `mcp-docs/docs/developer` no longer exist), in the READMEs, `CONTRIBUTING.md`, `SECURITY.md` and the README that `new-server.sh` generates.

## 2.0.0 - 2026-11-09

- CC-249, the gateway connects to the server by its address: the server needs no certificate from the internal CA, no mTLS and no policy data
  address. `application.yml` loses the TLS bundles, `server.ssl.client-auth`, `policy-data.*`, `manifest.internal-url`, the Redis block and the cursor key
  mapping (the starter reads `MCP_TLS_*`, `MCP_PLAIN_HTTP`, `MCP_STATE_DIR`, `MCP_REDIS_*` and `MCP_PAGING_CURSOR_KEY` itself); `MCP_GATEWAY_JWKS_URI` is the public
  `https://<domain>/.well-known/mcp-jwks.json`. The server serves `GET /.well-known/mcp-manifest` and takes `POST /.well-known/mcp-policy-data`.
- `deploy/`: `compose.yaml` has the server and a state volume only (no Redis service), `certs/` is optional (your own certificate), `server.env` has the JWKS
  address, the system address and optional TLS and Redis lines. The systemd unit has `StateDirectory=`. `deploy/README.md` is the new procedure: the author
  starts the server, the operator enters its address in the portal and approves the connection after comparing the fingerprint from the server log. The
  certificate from the internal CA and the registration of the manifest from the pipeline with the CI certificate are gone.
- `Dockerfile`: a writable state directory `/var/lib/mcp/state` (a volume) for the generated certificate.
- Tests: `ManifestTest` reads the well-known path with a token of the purpose `manifest`; `ProductionConfigurationTest` checks that no client
  certificate is required; `GatewayOnlyAccessTest` covers the purposes of tokens and the stale policy data.

- Removed `mcp-stub-backend` (module, `Stub backend` and `Local stack` run configurations, the `stub` profile of `deploy/compose.yaml`) and
  `tests/new-server-test.sh`: test material does not belong in the repository users copy. Both are in `mcp-e2e` now (`stub-backend/`
  and `tests/new-server-test.sh`, which runs against `../mcp-server-template`). The `generator` job of the three CI files is gone with the
  test. In-process tests keep their own `StubBackend` in `mcp-app`.
- The scope mapping of LocalGateway moved from `local/` to `.run/scope-mapping.json` and its generated env file to `local-gateway.env`
  in the project directory, as in the other servers; the `local/` directory is gone.

Dynamic servers: built on `mcp-platform-starter` 4.0.0 (contracts 7.0.0). The template is the reference for a new server, which is added
to a running platform and removed again without a restart. Major release: generated servers from 1.0.0 do not carry over (see the
migration guide in the CHANGELOG of `mcp-starter-lib`, 4.0.0).

- The server's own policies: `mcp-app/src/main/resources/mcp/policies/` with `schema.cedarschema` (one namespace, `Example`),
  `resource-types.json` (`idPattern`, `scopePattern`, `classification`, parent) and `read.cedar` and `update.cedar` with namespaced
  actions. The rules for restricted data and for the service account are generated by the platform and are not in the template. The
  resolver description gives records and projects their `scopes`; argument limits take the id pattern from the declared type
  (`@ArgumentLimits(resourceType = ...)`).
- `ExamplePolicyTest`: decisions of the policies with `PolicyDecisions` in plain JUnit (groups, scope in and out, restricted data,
  service account, client, override). `TestGateway` serves the scope mapping of `SampleScope`; the tool schemas are tested in `mcp-app`,
  next to the policies.
- Settings: every `MCP_POLICY_*` and `aiwcorpo.mcp.platform.policy.*` is gone; `MCP_GATEWAY_POLICY_DATA_URL` and `MCP_GATEWAY_TLS_NAME` are
  new. The manifest carries the policies and their hash and is written in every build, so a policy that does not validate stops it.
- `new-server.sh <system> [target-dir]`: any system id the contracts allow (the pattern is read from the contracts jar), no list of systems,
  no `--trial`, no profiles for jira, confluence, gitlab, servicedesk and opensearch (the servers of those systems are repositories of
  their own). The Cedar namespace is renamed with the system, `LICENSE` is copied unchanged, the compose file starts at `0.1.0`.
- `mcp-stub-backend`: a small stand-in for the system, so the server runs end to end without one. IntelliJ run configurations (`.run/`)
  start it with LocalGateway (server policies, `local/scope-mapping.json`) and the server in the dev profile.
- The stub backend answers `GET /api/me` (whoami), and the broker system is registered as `generic-rest` with `user-secret` and `whoami`
  (contracts CC-247); without `whoami` the broker stores the token unverified.
- `deploy/`: `compose.yaml` with `server.env` and `certs/` (profile `stub` for the stub backend), the steps to add a server to the platform
  and to remove it, the policy data address in the systemd environment template; the release workflow checks that the compose file pins
  the released version.
- Verified on the built jar: the starter finds the policies in `BOOT-INF/classes` of the server's jar and no jar in `BOOT-INF/lib` ships
  `mcp/policies`.

## 1.0.0 - 2026-11-04

First public release. Built on `mcp-platform-starter` 3.0.0 (contracts 6.3.2).

- Template of a native MCP server: a working server for the placeholder system `example` (Jira resource model) with sample tools
  (`get_record`, `search_records`, `list_comments`, `get_comment`, `update_record`), tests against a stub backend and the
  CI entry point `ci/run.sh`. `new-server.sh [--trial] <system> [target-dir]` generates a server for a system known to the
  contracts (jira, confluence, gitlab, servicedesk, opensearch) or a throwaway one with `--trial`.
- Generated servers start at version `0.1.0-SNAPSHOT` regardless of the template version, and get their own English `README.md`
  and `CHANGELOG.md`.
- The sample server carries the patterns of the full servers: a version probe (`ExampleCapabilityProbe`), a write gate that fails
  closed on an unknown version (`ExampleWriteGate`), a list paged by cursor (`CursorCodec`, `PageFiller`, `PagedResult`) and child
  ids checked against the judged record (`get_comment`).
- CI images are pinned by digest, GitHub actions by SHA; a separate `release.yml` workflow (ghcr.io image, manifest and CycloneDX
  SBOM) is copied into generated servers. `ci/run.sh generator` builds and tests a server for every system.
- Apache-2.0 licence, NOTICE, SECURITY.md, CONTRIBUTING.md.
